# Identity foundation and operator bootstrap

This milestone stores identity only. It does not authenticate requests or enable
registration, approval, account management, or OIDC. The API's write resolver
remains deny-by-default. Existing public business reads must not join or return
these tables; protect operational reads before using real identities/data.
The independently operated Telegraf/PostgreSQL bot is unchanged and remains
operational until a separately verified cutover. No import or deployment occurs.

## Stored invariants

- `users.id` is an internal text key, generated by D1 as 16 random bytes encoded
  in lowercase hex when omitted. Trusted callers may also supply generated
  opaque IDs (e.g. UUIDs). Never use Telegram IDs as User keys.
- Status defaults to `pending`; CHECK permits only `pending`, `active`,
  `rejected`, `disabled`. Nullable role CHECK permits only `admin`, `supervisor`,
  `sales_force`. Both active **and disabled** require a role: disabling retains
  the assigned role, and reactivation can restore access without guessing one.
- Pending/rejected may have no role. The schema does not require their role to
  be null; lifecycle operations must clear/assign roles according to policy.
- Optional `sales_force_id` references an existing business staff record with
  restrictive FK actions. It is deliberately **not unique**. Provisionally, one
  User can reference zero or one SF; multiple Users can reference the same SF.
  This is storage flexibility, not permission to share staff access. Confirm
  cardinality and reassignment/history rules before approval/submission. A true
  many-to-many association would require another migration; adding uniqueness
  later requires reviewing/deduplicating existing links. Admin/Supervisor do not
  need SF links, and a Telegram profile never creates/claims an SF record.
- `telegram_identities.user_id` is both PK and restrictive User FK, giving at
  most one Telegram account per User. Unique `telegram_user_id` prevents an
  account from belonging to multiple Users. A User can exist without a Telegram
  identity during controlled provisioning; registration must create both
  atomically. No independent surrogate identity ID is needed for this MVP.
- Bot API user ID is positive canonical decimal **text** (`[1-9][0-9]*`), without
  signs, whitespace, leading zeros, decimal points or exponents. No arbitrary
  32-bit or JS-safe-integer bound is imposed on storage. Bind as a string; SQL
  text affinity cannot recover precision already lost by a numeric caller.
- Username/first/last name are nullable, non-unique display snapshots, never
  matching keys, credentials or evidence of employment. Store no bot tokens.
  OIDC `(issuer, sub)` is a separate, later namespace; there is no subject column
  or inferred equality with Bot API IDs.
- New tables require integer-millisecond creation/update timestamps, defaulting
  to D1 receipt time (second precision). Writers must set `updated_at` explicitly
  on changes. There is no update trigger or ORM-only automatic timestamp rule.

The database supports pending → active(role), pending → rejected, active →
disabled (retain role), disabled → active, and rejected → pending. The latter
is **not approved reapplication policy**. CHECKs validate stored states, not
actor authorization, prior-state transitions, role-change history or last-Admin
protection. No RBAC hierarchy is implied. Requiring SF for report-capable users
belongs to the future authorized operation, not a speculative storage rule.

## Controlled first-Admin provisioning

Documentation-only operator procedure, not an application service. Use a
restricted change record and an authorized D1 operator; no public endpoint,
secret allowlist, privileged environment switch or application bypass exists.
Do not run against a remote database as part of this PR.

1. Obtain approval for the operator, target person, database/environment, and
   reason in a restricted change record. Verify ownership of the person's Bot
   API ID out of band through a trusted authenticated Telegram interaction;
   never trust a username, display name, forwarded contact, or OIDC subject.
   Do not copy teammate seed values. Choose a fresh internal UUID and retain it
   in the restricted record for retries. This is not the Telegram ID.
2. Apply/review migrations, confirm the intended environment, and take the
   approved D1 backup/recovery checkpoint. Stop competing access-management
   writes during provisioning. Inspect existing Users/Telegram bindings first.
   If any Admin is already active, use later audited administration instead;
   this procedure must not be used for recovery or promoting existing accounts.
3. Copy the SQL below to a private temporary file outside the repository,
   replacing both placeholder strings with validated values. Validate the
   internal ID as a fresh UUID and Telegram ID as canonical decimal text before
   substitution; do not interpolate untrusted SQL. Retain the **same** internal
   ID on retries. First rehearse with synthetic IDs against a local D1 sandbox:
   `pnpm --filter @sales-visit/db exec wrangler d1 execute DB --local --config wrangler.local.jsonc --file /absolute/private/bootstrap.sql`.
   A future remote execution requires separate approval and explicit reviewed
   database/config selection; never simply change this command in automation.

```sql
INSERT INTO users (id)
SELECT '<internal-user-id>'
WHERE NOT EXISTS (SELECT 1 FROM users WHERE status = 'active' AND role = 'admin')
ON CONFLICT(id) DO NOTHING;

INSERT INTO telegram_identities (user_id, telegram_user_id)
SELECT id, '<telegram-bot-user-id>' FROM users
WHERE id = '<internal-user-id>' AND status = 'pending' AND role IS NULL
ON CONFLICT(user_id) DO NOTHING;

UPDATE users SET status = 'active', role = 'admin', updated_at = unixepoch() * 1000
WHERE id = '<internal-user-id>' AND status = 'pending' AND role IS NULL
  AND sales_force_id IS NULL
  AND EXISTS (SELECT 1 FROM telegram_identities
              WHERE user_id = users.id AND telegram_user_id = '<telegram-bot-user-id>')
  AND NOT EXISTS (SELECT 1 FROM users WHERE status = 'active' AND role = 'admin');

SELECT u.id, u.status, u.role, u.sales_force_id, t.telegram_user_id
FROM users u LEFT JOIN telegram_identities t ON t.user_id = u.id
WHERE u.id = '<internal-user-id>';
```

4. Verify **exactly** the intended active Admin + Telegram binding, null SF,
   one active Admin overall, and empty `PRAGMA foreign_key_check`. Zero updated
   rows is not proof of success: inspect every value. Stop on any SQL error,
   pre-existing ID, mismatched binding, or unexpected state; do not overwrite,
   delete, or promote existing accounts to repair it. The fresh-ID precondition
   is operator-verified, not proven by this SQL.
5. Record operator identity, reviewer, target internal ID, action, UTC time,
   environment/database, reason/change ID, before/after state and command
   result in the restricted change record. Keep real Telegram IDs and command
   output out of Git, public PRs and general logs. Remove the private working
   file per retention policy after recording approved evidence.

Each SQL statement is safe to retry with the same verified IDs; there is no
upsert that replaces an identity or elevates an existing disabled/rejected
account. Activation's single-statement `NOT EXISTS` guard prevents a second
first Admin. This multi-statement runbook is **not an atomic provisioning
transaction**: interruption can leave a pending User or identity, but never an
active unlinked bootstrap User. Inspect partial state before retrying. Conflicts
fail or leave state unchanged; they must be investigated, not ignored.
Tests exercise this exact template locally, including retries and conflicts.
This is minimal operator support, not a general-purpose seeder or account tool.

### Audit and recovery release gates

No audit table is added: no application lifecycle writer exists in this PR.
Bootstrap accountability is an external restricted operator change record,
not a database-enforced/tamper-proof audit guarantee. If that process cannot be
provided, do not provision. Do not describe `updated_at` as an audit trail.

Before application registration/approval or account changes ship, add narrowly
scoped access-management audit writes **atomic with** mutations: event ID,
action, actor User (or explicit operator identity for bootstrap/recovery), target
User, previous/new status/role/SF/identity association, UTC event time, reason,
and request/correlation/change ID. Restrict access and retention; never record
raw tokens, secrets, whole Telegram updates or unnecessary profile payloads.
Cover approval, rejection, role/link changes, disable/reactivate and recovery.

Later lifecycle operations must enforce the last-active-Admin rule atomically,
including concurrent disable/demotion, and define verified operator recovery for
lost/compromised Telegram accounts. Recovery must revoke old sessions/bindings,
retain history and produce audit evidence; this first-Admin template is **not**
a recovery bypass. Define rejected-account reapplication policy, exclusive-role
permissions, SF verification/cardinality, retention and concurrent authorization
checks before implementing operations. OIDC linking, sessions, signed-claim
validation, two-channel pairing and read authorization remain separate milestones.
