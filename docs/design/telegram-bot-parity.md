HARI is case-insensitive senin/selasa/rabu/kamis/jumat/sabtu/minggu. Monorepo `/jadwal [HARI|semua] [after=KURSOR]` requires day/semua before cursor. Named `/jadwalsales` options can occur in any order. Planning IDs/cursors use exact simple ASCII tokens or canonical `~` + unpadded base64url UTF-8. They are not usernames, Telegram IDs or credentials. Names consume remaining text, spaces allowed; underscores are not required.

## Account transition and release policy

Only active Admin can list/manage users, including empty pages and repeated operations. Target is an existing canonical Telegram identity, never username or internal User ID. The private BotIdentity Service Binding is the sole administration transport; no public HTTP endpoint was added. Actor is extracted from the verified human Telegram sender, not target arguments; API rejects claimed role/status/SF actor fields.

| Operation        | Transition / invariant                                                                                                                                                                                                                     |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| register         | New→pending; all existing statuses unchanged                                                                                                                                                                                               |
| approve / reject | Pending/unassigned→active(role/link) or rejected; existing behavior unchanged                                                                                                                                                              |
| setrole          | Active only; admin/supervisor or sales/sales_force + existing verified business SALES_FORCE_ID                                                                                                                                             |
| disable / enable | Active→disabled / disabled→active; retain role and SF association                                                                                                                                                                          |
| Repeat           | Same desired state succeeds without another update/audit; conflicting/invalid transitions return Indonesian guidance                                                                                                                       |
| Admin protection | No demotion/disable of any active Admin, including self; explicit transaction-time count guard prevents removal of last active Admin. Recovery remains a separate reviewed operator procedure, not bootstrap reuse                         |
| SF protection    | Cannot replace an existing nonnull link, claim another account's link (even disabled), or silently release a link when moving to admin/supervisor. This is a conservative application policy, not a new schema uniqueness/cardinality rule |

Exact new grammar: `/users [KURSOR]`, `/setrole TELEGRAM_ID admin|supervisor`, `/setrole TELEGRAM_ID sales SALES_FORCE_ID` (sales_force alias supported), `/disable TELEGRAM_ID`, `/enable TELEGRAM_ID`. Like existing approval, SF argument is a simple whitespace-free ID, trimmed by the identity contract, **not** the planning `~` token format. Verify identity and SF ownership out of band; no automatic staff-verification service exists. Pages are live snapshots ordered by internal ID, not reference creation-date order; cursors are not target identifiers or permissions.

Every mutation checks current actor/status, target transition, Admin protection and SF claim inside one serialized D1 batch. Audit INSERT captures exact before/after status/role/link; UPDATE is gated by its unique event ID. Failures roll back both. A concurrent call ordered before revocation can succeed; calls ordered after are denied. No persistent actor cache. Telegram delivery is not transactional; inspect profile/list after ambiguous failure. Retries of the same desired state add no event; delayed opposing operations are new transitions, not deduplicated Telegram receipts.

Migration `0005_good_puff_adder.sql` is a new forward migration extending audit actions to setrole/disable/enable. SQLite requires rebuilding the audit table to widen its CHECK; existing IDs, states, timestamps, restrictive FKs and target index are preserved. Foreign keys stay enabled; prior migrations are untouched. **Before any separately approved release**, back up/review the target and apply 0005, then release API before Bot. Existing deployment helpers discover checked-in migration names and refuse pending/unexpected remote migrations; no safeguards/configuration were changed. No remote action ran here.
