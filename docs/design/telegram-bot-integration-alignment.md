# Telegram Bot integration and domain alignment

**Iteration 3 — proposal for review, not implementation approval.**

## 1. Executive summary

Preserve the independently developed bot's Indonesian command vocabulary, registration and approval workflow, guided data entry, preview, confirmation, and cancellation UX. Move business operations and authorization into the Hono API, with D1 as the only operational database. Adapt handlers incrementally to the existing grammY Worker rather than importing the Node.js application or rewriting all workflows at once.

The principal blockers are semantic, not framework-related:

- The external bot's `users` combines Telegram account, access role/status, and Sales Force code. The monorepo has only a Sales Force business record, not an authenticated User.
- External Outlet business ID, internal PostgreSQL ID, and No. RS are distinct. The monorepo only has an opaque internal ID and name.
- Recurring weekday assignments exist externally but not in shared contracts, D1, or the API. They are not actual Visits and do not currently restrict report submission.
- External `sales_visits` combines a Visit with three category-level Stock/Selling/Sellout triples, period, balances, status observations, and Total Belanja. The monorepo intentionally separates Visit and Stock Report and only supports product-level quantity observations.
- OIDC `sub` is an opaque string, **not a verified substitute for Bot API `User.id`**. Preserve both namespaces and prove the association before granting Web access to a Bot-registered User.

First deliver an authenticated slice: register in Telegram → Admin approves and associates Sales Force → Telegram OIDC Web login → submit a minimal Visit from either channel → read it from the authorized Web UI. Extend to optional Stock Reports next. Do not block this slice on undefined financial metrics or port every administrative command first.

### Registration and account transitions

Implemented transitions are `new → pending`, `pending → active(role)` or `rejected`, `rejected → pending` by re-registration, and `active ↔ disabled` by Admin. Role changes require active status. Approval does **not** populate `salesforce_code`; there is no command to assign it. An approved sales user can submit a report without a code but cannot view their own schedule without one. Code provisioning therefore remains an out-of-band prerequisite for schedules, not a complete onboarding flow.

Roles/statuses are TypeScript unions and command/service checks; PostgreSQL `users.role`/`status` are unconstrained `VARCHAR`, not checked enums. An existing active Admin is required for in-chat approval. Package scripts expose Admin seeding, not a public first-admin registration path; seed personal values and actual operational provisioning were not audited.

### Sales Visit wizard: exact input sequence

| Step                | Captured field / behavior                                                                                     |
| ------------------- | ------------------------------------------------------------------------------------------------------------- |
| Entry               | Recheck active sales account; request Outlet business ID.                                                     |
| Outlet              | Digit-only text; stored as string. Existence is checked only when generating preview and again at submission. |
| Period              | `Number(text)` must be an integer from 1–5; described as week-of-period/month in prompts.                     |
| DigiPOS             | Balance input; see amount parser below.                                                                       |
| Perdana SA          | Three independent inputs in one message: `Stock Selling Sellout`.                                             |
| VF Data             | Same triple.                                                                                                  |
| VF Voice            | Same triple.                                                                                                  |
| CVM, Voice, Digital | Three separate Y/N answers for outlet activity.                                                               |
| Total Belanja       | Amount input, then Outlet lookup and full preview.                                                            |
| Confirmation        | `/konfirmasi` writes; `/batal` discards. No back/edit step or explicit visit-date prompt.                     |

Validation distinctions matter:

- Amount parser trims and removes **all periods**, then accepts digits only and a JS safe integer. Thus it accepts nonnegative integer values including zero, not decimal currency; dotted grouping is permissive rather than a validated locale format. Do not transfer that parser as an approved monetary rule.
- Product parser accepts exactly three nonnegative safe integers separated by spaces and/or commas. It does not calculate Sellout or validate a relationship between the three quantities.
- Y/N is case-insensitive, with no other accepted answers.
- Final Zod service requires nonblank Outlet ID, period 1–5, nonnegative integer quantities/amounts, and booleans. It does not require a numeric-only Outlet ID as the wizard does.
- Outlet create/edit service only requires nonblank business ID, No. RS, and name; business ID uniqueness is checked and enforced in SQL. No. RS is not unique and has no numeric/phone validation. This differs from digit-only wizard entry.
- SQL quantities are PostgreSQL `INTEGER` (narrower than JS safe integers); amounts are `NUMERIC(15,2)` (allows decimals that the wizard rejects). Extremely large wizard-valid values can therefore fail persistence.
- Submission checks User status/role and Outlet existence, **not assignment or scheduled day**. No validation ties period to visit date. No price, stock movement, or Total Belanja calculation exists.

### Persistence, state, and runtime

- Parameterized `pg` queries persist master data and registrations. Report confirmation inserts **one wide `sales_visits` row**, referencing internal User and Outlet IDs. Nine quantity fields, two monetary fields, three booleans, and period are mandatory; SQL supplies defaults for quantities/amounts if omitted outside the service.
- `visit_date` defaults to database `CURRENT_DATE`; repository accepts an optional date but wizard/service do not supply one. `created_at`/`updated_at` use `TIMESTAMPTZ`. Month/year are not independent columns: help says they follow report creation date. Database timezone is not fixed in the reviewed connection config; do not assume it is Jakarta.
- Report repository implements `findById`, `findByUserId`, `findByOutletId`, but no user-facing history commands or Express business routes expose them.
- Telegraf `session()` uses default in-memory storage, and WizardScene stores the draft in `ctx.wizard.state`. `/batal` deletes `session.__scenes` directly. No durable session store, expiration, update deduplication, or report idempotency key is configured. Default framework session key is user + chat, not just user [T4].
- Node.js process loads dotenv, opens a PostgreSQL pool, connects to the administrative `postgres` database to potentially create the application database, runs filesystem migrations at startup, starts Express, and calls `bot.launch()` for long polling. SIGINT/SIGTERM stops the bot/server/pool.
- Express only exposes `/api/health`; `botStatus.running` is a process flag, not a database or Telegram delivery readiness check. There is no Web authentication API or existing report API to adopt.
- Migration 002 backfills normalized Outlet/User FKs from legacy business ID/code, aborts if links are missing, and drops duplicated schedule columns. Conflicting metadata for one business ID can defeat its `SELECT DISTINCT` insert into a unique business-ID table. Migration runner wraps files in transactions while 002 also has `BEGIN/COMMIT`; this transaction ownership should not be copied. No migration was executed for this review.

### Implemented vs planned and security/reliability gaps

README marks Sales Visit recording as planned, but E5/E6 implement it. History **repository reads** exist, while history chat UX, product management, Excel export, and reporting/dashboard remain unimplemented in the inspected bot. Schedule viewing is implemented; schedule create/edit/delete commands are not. The existence of seeder scripts is not an interactive schedule management workflow.

Confirmed gaps to address during adaptation:

- No private-chat restriction: account lists and reports can be requested/replied to in a group by an authorized actor. Recommend private-only onboarding, administration, and report entry for MVP.
- No durable conversation progress or confirmation idempotency. A committed insert followed by failed Telegram reply can leave the user at confirmation; retry can create a duplicate.
- Authorization is scattered through handlers and services. Final report service correctly rechecks status/role, but there is no shared API policy, audit trail, or Web session enforcement.
- No deliberate last-active-Admin recovery policy. Blanket protection of active Admin targets prevents ordinary demotion/disable, including incident response.
- Some errors are logged raw and surfaced using `error.message`; there is no registered global bot error boundary in E1. Lists other than the aggregate schedule output have no length handling/pagination. Do not log tokens, raw updates, or personal report payloads in the target.
- Runtime database creation/migration needs privileges inappropriate for a request-serving Worker. No real automated tests are configured (`test` deliberately fails). Source behavior is not evidence of reliable deployment.

### What the monorepo actually supports today

- M2/M3 support SF, Outlet, Product, Visit, Stock Report and per-product nonnegative quantity. IDs are nonblank opaque strings; DB timestamps are integer milliseconds. Same-Outlet linked-report FK is enforced. There are no Users, Telegram identities, roles, schedules, or financial/status metric fields.
- PR #2 provides strict `POST /visits` (optionally including a linked Stock Report) and `POST /stock-reports` (independent or linked). Inputs cannot supply reporter, channel, or arbitrary extra fields. Items must be 1–100 distinct products; references and timestamps are validated. D1 batch makes Visit + optional report atomic. Idempotency is scoped to operation, SF, channel and UUID; same normalized payload replays, changed payload conflicts.
- Deployed default identity resolver denies **all writes**. Its test-injected `TrustedIdentity` contains only SF and channel; it is not implemented authentication or complete authorization. Reads are currently unauthenticated. Future auth must cover reads as well as writes, including replay paths: replay lookup currently precedes reference validation.
- Web uses synthetic fixtures plus browser-local Visit/linked-report storage, not these API operations. Form lets users choose SF manually; it records WIB visit time separately from local submission time. Local storage validation is stricter than the domain for its own linked reports (reporter must equal visitor). Do not promote that prototype restriction into the API.
- Web login is an explicitly nonfunctional email/password validation demo. It sends/stores no credentials, but its fields conflict with the accepted MVP identity direction and should be replaced, not connected to a password backend. Router navigation/demo access is not authorization.
- Current monorepo bot verifies webhook secret and only offers `/start`, `/help`, and an unavailable-reporting text fallback. It does not register or submit users/reports yet.

## 4. Telegram-first authentication architecture

### Accepted constraints

Telegram handles registration and Admin approval; Web uses Telegram OIDC, with no application password or mandatory email. One internal User serves both channels and links to Telegram identity rather than using Telegram ID as PK. D1 is authoritative, Hono owns business operations and permissions, and both clients use identical business rules. Workers remain the target; grammY is the current ADR-0005 choice. Visit and Stock Report remain separate with optional linking (ADRs 0002–0005). Outlet accounts/self-reporting remain deferred.

### Verified Telegram claims and limits

Provider sources [T1–T3] establish:

| Identifier / claim                   | Verified meaning                                                                                                   | Safe usage                                                                                                                                                                          |
| ------------------------------------ | ------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Bot API `User.id` / update `from.id` | Unique numeric Telegram user/bot identifier; at most 52 significant bits, not necessarily 32-bit [T2].             | Actor lookup only after webhook authentication; reject bot actors for human onboarding. Store as canonical decimal text. Never identify actor using command arguments or `chat.id`. |
| OIDC `sub`                           | Unique subject returned with `openid`; discovery advertises public subjects [T1, T3].                              | Store exact opaque string, namespaced by issuer. Never cast to number or compare to Bot ID. Public subject type does not assert numeric equality with another API.                  |
| OIDC profile `id`                    | `profile` scope documentation explicitly lists user ID and `id`; example has distinct `sub` and numeric `id` [T1]. | Candidate numeric Telegram user-ID bridge, **not `sub`**. Verify signed claim and provider relationship, not an unsigned browser profile.                                           |
| `preferred_username`, names, picture | Optional profile/display claims [T1].                                                                              | Never account matching keys, role assignments, or proof of staff employment.                                                                                                        |
| `aud`                                | Intended OIDC client; Telegram validation guidance says check against configured Bot ID [T1].                      | Token audience check, not the end user's Telegram ID. Use BotFather-issued client configuration.                                                                                    |

**Documentation discrepancy / release gate:** live discovery `claims_supported` did not list `id` at review, whereas Telegram Login's profile table and ID-token example do. The reviewed docs do **not explicitly guarantee `sub == Bot User.id`** or provide a cross-API equality contract for the profile `id`. An example is not such a guarantee. Do not ship a join that guesses either relationship.

**Recommended safe initial linking:** bind a validated `(issuer, sub)` to the existing Bot-registered User through a short-lived, single-use pairing challenge confirmed in the Bot's private chat. The browser initiating OIDC must approve the binding and the verified Bot actor must match the challenge's intended User. Store the challenge hash, initiating browser transaction, subject, expiry and consumed state server-side; show a confirmation in both channels, reject cross-user/previously-bound subjects, and atomically consume it. Do not make a copyable link alone sufficient to overwrite an association. No email/code-as-staff-identity fallback.

Before implementing this, timebox an OIDC interoperability check with consenting test accounts (including one without a username): verify requested `openid profile`, actual signed claim types, issuer/audience, profile `id` vs authenticated Bot `from.id`, and nonce behavior. Do not store raw tokens in the PR. If authoritative provider clarification establishes the profile `id` relationship, review a simpler first-login mapping by **validated profile `id`** to an existing Bot identity and bind `(iss,sub)` atomically. Observed equality alone is not proof of a universal guarantee. Until that gate is met, explicit two-channel pairing is the safe path; the slice can work without assuming equality.

Subsequent login resolves the stored `(iss,sub)` association; if any supplied verified numeric ID conflicts, deny and investigate rather than relink. Missing `id` is not a reason to parse `sub`. Unregistered Web logins get a register-in-Bot instruction, not an automatically active new account. Binding an OIDC subject never approves a pending User.

### Web authentication (recommended)

1. Keep the Vite dashboard static. Let API Worker expose login start/callback/logout/session endpoints. Configure fixed Allowed URLs in BotFather, secrets in Worker bindings, and a fixed post-login return path to prevent open redirects.
2. Use Authorization Code Flow, `openid profile`, S256 PKCE, random one-time state and nonce bound to the initiating browser. Request no phone/email scope and no bot-message scope unless separately justified; the user has already started the Bot.
3. API exchanges the code using server-side client authentication. Validate JWT signature against configured Telegram JWKS, allowlisted algorithm (initially RS256), exact issuer, audience/client binding, expiry, reasonable issued-at/skew and nonce. Handle JWKS rotation with bounded refresh; fail closed. Telegram currently has no separate UserInfo endpoint [T1]. Never trust the frontend's decoded claims or use legacy Login Widget HMAC validation for an OIDC JWT.
4. Resolve/pair identity as above, then check current D1 status. Issue a random opaque Web session only for eligible active accounts; use a separate narrowly scoped browser transaction for pairing or status display. Store only session-token hashes, with expiry and revocation.
5. Prefer same-site Web/API custom domains and an API-host-only `Secure; HttpOnly; SameSite=Lax` cookie. If using credentialed cross-origin fetch, allow only the exact Web origin, never wildcard. Require CSRF token plus Origin checking for mutations; logout is a CSRF-protected mutation. Preview-domain/cross-site cookie behavior must be tested before public use, not patched with a JS-readable token in localStorage.
6. Every protected API request re-resolves session → User and reads current account status, role and SF association from authoritative D1. Deny pending/rejected/disabled regardless of session lifetime. Do not embed authoritative roles in long-lived JWTs or trust UI role labels. Expire/revoke sessions on logout; revoke all sessions on disable as defense in depth.

### Bot authentication and API trust boundary (recommended)

```text
Telegram HTTPS update → Bot Worker verifies webhook secret / allowed update shape
                     → private-chat handler extracts actual from.id
                     → internal Service Binding operation
                     → API resolves Telegram identity → User → permissions
Browser → Telegram OIDC callback → API validates token/link → session cookie
Browser → public API → session/User lookup → same operation/permissions → D1
```

Webhook `secret_token` verifies requests to the Bot Worker [T2]; it is **not** per-user approval, an OIDC token, or a public API bearer credential. The existing Bot Worker already checks its configured secret before grammY work. Retain that behavior, constrain update size/types, handle missing `from`, and do not derive actor from forwarded contacts, message text or an Admin's target-ID argument.

Use a dedicated internal Worker service/RPC entrypoint only bound to `apps/bot` for the actor-bearing envelope. The public API must never accept a caller-selected Telegram/SF/User ID via a spoofable header or public equivalent route. Service caller authentication establishes _which Worker_ sent the envelope; API still resolves _which User_ acted and checks permission for this operation. Bot has no D1 business repositories or PostgreSQL credentials. Channel is fixed to `telegram` internally, `web` for browser session operations.

### Authorization, distinct from authentication

A valid Telegram identity/session proves who is acting, not what they may do. **Recommended starting policy for review:**

| Capability                             | Admin                                                      | Supervisor                             | Sales Force                                 |
| -------------------------------------- | ---------------------------------------------------------- | -------------------------------------- | ------------------------------------------- |
| Self-profile/status/logout             | Yes                                                        | Yes                                    | Yes                                         |
| Approve/reject, role/status management | Yes, audited with last-Admin safeguard                     | No                                     | No                                          |
| Operational report/schedule monitoring | Yes                                                        | Yes; territorial/team scope unresolved | Own; visibility/assignment scope unresolved |
| Outlet master mutations                | Yes                                                        | No                                     | No                                          |
| Submit Visit / Stock Report            | Not automatically; only if explicitly granted with SF link | Same                                   | Active + SF link required                   |

Pending/rejected/disabled actors may only use narrowly allowed onboarding/self-status operations, never operational reads/writes. Keep Admin/Supervisor SF links optional: having a link does not itself grant submission. Define whether roles are exclusive and whether those roles may act as SF before enabling that behavior. Start with the external bot's exclusive three roles, not a generic RBAC platform.

Check permissions **before idempotency replay** and again at mutation execution. Mid-wizard disable or role change must block confirmation, and an old Web session must observe the new role on its next request. For mutations, use an atomic conditional authorization guard/version check with the write so concurrent disable/demotion cannot race a stale authorization read. After the status-change commit, requests must not use stale caches/read replicas for permission decisions. An already completed operation cannot be retroactively undone; specify and test concurrent ordering. Map unauthenticated to 401 and authenticated-but-forbidden to 403 without revealing private records.

### Account lifecycle and recovery safeguards (recommended)

- Registration is idempotent on Telegram identity and cannot set role/status/SF from user input. Preserve rejected → pending reapplication only if the team approves that policy; disabled cannot self-reactivate.
- Admin approval atomically sets status/role, validates optional SF association, and records actor/time. For Sales Force approval, require an existing verified SF association or include an explicit reviewed provisioning step. Do not create/claim staff records merely from Telegram name/code text.
- Bootstrap one D1 Admin via a controlled, audited one-off operator procedure; no permanent environment allowlist bypass and no public bootstrap endpoint. Do not ship teammate seed identities.
- Protect against disabling/demoting the final active Admin, but allow authorized incident response against other Admins. Require explicit confirmation, audit, and an operator recovery procedure. Telegram account loss/replacement requires manual verified relinking, old session revocation and retained history, not username matching.

### Telegraf vs grammY tradeoff

Telegraf middleware, `ctx.reply`, and command parsing are familiar to grammY, so much of the handler **intent** is portable. Telegraf `Scenes.Stage`, `WizardScene`, `ctx.wizard.next/state`, and `__scenes` internals are not grammY-compatible. The largest change is durable state/authorization separation, which would still be necessary even if Telegraf were retained.

**Recommendation:** keep grammY per ADR-0005, reuse pure helpers/text and refactor one workflow at a time. For a short university project, an explicit versioned state machine stored via API is easier to inspect/test than persisting suspended JavaScript closures. grammY storage/conversation plugins are alternatives for a later implementation evaluation, not dependencies authorized here; plugin replay effects would need special care around API writes [T5].

Keeping Telegraf behind a Workers webhook adapter could preserve Scene code temporarily, but requires a runtime compatibility test, persistent session adapter, concurrency safeguards, and an ADR-0005 amendment. Neither repository demonstrates that deployment. Do not declare Telegraf intrinsically impossible on Workers or assume importing the whole Express/pg app will work. Avoid maintaining two frameworks in the final bot.

### Persistent conversation and retry behavior

- D1 draft accessed through internal API operations is the recommended single-store solution. Store data/step identifiers, not framework context objects. Deployment must reject/migrate incompatible flow versions with a clear restart message. Set a reviewed TTL and support cancel/restart.
- Updates can overlap. Advance draft only with expected revision and an update receipt in an atomic operation. Concurrent/duplicate update processing must not advance two steps. For out-of-order/conflicting input, preserve draft and ask the user to retry rather than applying an answer to a guessed step. Never use a permanent global maximum `update_id` to discard all older updates.
- Persist one submission UUID and normalized visit/report timestamps before first confirmation. Reuse on retries through existing API idempotency. Store committed result before final success reply; a reply failure must not create a second report. Duplicate notification delivery is tolerable if bounded; duplicate business records are not.
- Idempotency keys only deduplicate the same logical request within its existing operation/SF/channel scope. Separate Web and Bot entries are not automatically duplicates; do not merge legitimate observations based on Outlet/date/period without an approved rule.
- Preserve authorization recheck at confirmation, not just flow entry. Disabled account may retain an expired/blocked draft, never a permission snapshot.
- Acknowledge webhook only after durable processing or durable handoff. On transient failures return a retryable response; on permanent rejected input send a safe explanation and do not repeatedly fail delivery. Leases must recover after crashes; an unexpired “processing” receipt must not cause silent loss. Do not promise exactly-once Telegram replies.
- Prefer this bounded synchronous flow initially. Durable Objects/Queues might simplify serialization/background delivery later, but add scope/cost. Do not introduce them without measured need; no extra business database.

### Cutover and existing data

No migration is performed in this milestone. Confirm whether there is real historical data, not just development fixtures. If import is required, plan an operator-approved **one-time** export, validation and D1 import with ID crosswalks, counts, FK checks and provenance. Do not translate PostgreSQL SQL directly: `BIGSERIAL`, `NUMERIC`, booleans, `TIMESTAMPTZ`, dates, timezone defaults, and transaction patterns require explicit mappings.

Block import of ambiguous category aggregates/date-only records until representation is agreed. Preserve a restricted read-only archive if retention requires it, **not** a second application data source. Never present fabricated timestamps or discard unmatched User/SF codes silently.

For the same bot token, stop Node long polling before setting the Worker webhook; Telegram polling and webhook delivery are mutually exclusive [T2]. Agree how to handle pending updates and warn users that in-memory drafts cannot be transparently transferred. Avoid `drop_pending_updates` unless explicitly approved. Use a separate test bot for development, no token in command transcripts. At cutover, only D1 receives writes. If rollback is needed, pause writes and revert the Worker release/restore validated D1 state, not resume an obsolete PostgreSQL writer.

## 7. Migration risks and tradeoffs

| Risk                                          | Mitigation / explicit tradeoff                                                                                                                                                                   |
| --------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Account takeover by guessed ID or username    | Signed OIDC validation, separate subject namespace, two-channel pairing until ID relationship is established, unique bindings, no auto-merge. Extra first-login friction buys a verifiable link. |
| Disabled user retains old permissions         | Authoritative D1 check on every protected operation including replays; no role cache; conditional mutation guard. Costs a lookup rather than trusting stale sessions.                            |
| Losing legacy report meaning                  | Validate family vs SKU and financial/period terms before schema extension/import. A smaller clearly labeled slice is preferable to fake parity.                                                  |
| Duplicate records or lost wizard steps        | Stable UUID/timestamps, D1 revision checks/receipts, recoverable processing leases, retry tests. More storage logic than memory sessions.                                                        |
| Admin lockout / compromised Admin             | Last-active-Admin safeguard plus audited operator recovery; do not copy blanket Admin immunity.                                                                                                  |
| Group-chat disclosure / excessive logs        | Private-only MVP flows, minimal metadata logs, paginated lists, generic external errors.                                                                                                         |
| Local prototype mistaken for production       | Replace SF chooser and password demo in auth milestone; label mock/demo routes; prohibit operational data before read authorization.                                                             |
| D1/platform limits and cookie/origin problems | Local Worker tests, bounded API/draft queries, preview auth tests, measure limits before deployment; no promise of unlimited free operation.                                                     |
| Too much migration scope                      | Authenticate one Visit end-to-end before schedule CRUD, metric extensions, exports, or framework plugins. Review with teammate in small PRs.                                                     |

### ADR proposals, not accepted ADRs

1. **Telegram-first User identity and Web OIDC sessions:** record the supplied accepted direction and review concrete linking, session/revocation, bootstrap and role decisions. Existing ADRs do not specify these details. Alternatives: unsafe subject/numeric conflation, or dual password identity (rejected by iteration constraints).
2. **Durable bot workflows through the API/D1:** record explicit versioned state/receipt approach and retry/concurrency tradeoffs after a small test. Compare a grammY plugin and optional serialization primitives. Keep grammY under ADR-0005; retaining Telegraf instead requires an explicit amendment, not an undocumented exception.
3. **Reporting measures and period semantics:** propose only after partner validation. A wide combined Visit report would conflict with ADR-0003; any approved extension must retain optional Visit↔Stock Report linking. Changes to reporter model or Outlet accounts must respect ADR-0004.

Do not mark any new ADR accepted based solely on this document. ADR-0006 describes an earlier static-first phase, not evidence that the post-PR-#2 write operations do not exist.
